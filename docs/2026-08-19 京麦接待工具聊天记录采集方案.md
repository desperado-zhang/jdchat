# 京麦接待工具聊天记录采集方案

文档日期：2026-08-19
当前分支：`feature/reception-chatlog-capture`
目标页面：`https://shop.jd.com/jdm/kefu/kf-manage-lite/#/UtilsSetting/ReceptionTools`
业务入口：接待工具 -> 聊天记录
当前结论：新需求应从原“咚咚实时工作台采集”拆出独立链路，围绕京麦“聊天记录”查询页做受控时间范围采集、去重和入库。

## 1. 需求变化

原方案围绕 `https://dongdong.jd.com/` 工作台：

```text
实时监听当前工作台收到的聊天记录
读取 window.session
解析 #t-chat-scroll 当前会话 DOM
可选被动监听 fetch/XHR/WebSocket
```

新需求变为：

```text
不再抓取网页实时聊天记录
从京麦“接待工具 / 聊天记录”页面采集一定时间范围内的客服客户聊天记录
点击列表行“查看”后，右侧抽屉中展示该会话最新聊天记录
采集后去重入库
```

因此需要新分支开发，不应继续把逻辑塞进现有咚咚工作台 DOM/session 采集路径。本分支默认只启用京麦聊天记录链路；旧 `dongdong.jd.com` 实时链路如需保留，必须拆成独立 legacy 开关并默认关闭。

## 2. 采集边界

### 2.1 允许

```text
在客服本人已登录京麦后台的浏览器页面内采集
读取聊天记录列表页自然返回的查询结果
点击“查看”打开当前页右侧聊天明细抽屉
读取右侧抽屉 DOM 中已经渲染的消息
被动截获页面自然触发的 queryList/queryChatLog XHR 响应
按用户指定时间范围、页数上限、会话上限低频采集
将规范化消息上报本机采集网关
幂等入库
```

### 2.2 禁止

```text
点击“发起新会话”
点击“举报”
导出平台数据
绕过京麦登录
复用 cookie、token、sign、aid 等鉴权参数到独立后端批量调用
从服务端直接模拟京麦接口批量拉取
高频翻页、并发打开、无限制遍历全部历史
自动发送、标记、转接、改客服状态
把客户 pin、订单、正文等敏感信息写入日志、文档或普通控制台输出
```

## 4. 网络接口观察

本方案只把以下接口作为页面自然请求的结构依据，不建议把鉴权参数拿到后端直接模拟调用。

### 4.1 会话列表

列表查询自然触发：

```text
GET https://kf.jd.com/waiterSession/jingmai/queryList
```

已观察查询参数：

```text
startTime=2026-08-19 00:00:00
endTime=2026-08-19 23:59:59
viewMode=1
page=1
pageSize=10
```

响应顶层结构：

```json
{
  "code": "string",
  "size": "number",
  "totalPage": "number",
  "waiterSessionList": [],
  "totalRecordNum": "number",
  "page": "number"
}
```

`waiterSessionList[]` 主要字段：

```text

cid
consultationDate
customer
evaluation

extFlag
gLevel
goodsName
groupId

promoteOrder

service

```

`cid` 是后续打开聊天明细的关键会话标识，应作为本链路 conversation identity 的核心组成。`cid` 只能在插件内存中用于计算哈希和关联 `queryChatLog` 响应，不能写入 `eventId`、日志、文档、`raw_json` 或普通接口响应。

### 4.2 聊天明细

点击列表行 `查看` 后自然触发：

```text
GET https://kf.jd.com/waiterSession/queryChatLog?cid=<redacted>
```

注意：`queryChatLog` 响应体本身不包含 `cid`。插件必须在点击 `查看` 前，从当前列表行或最近一次 `queryList.waiterSessionList[]` 建立 `row -> cid` 的内存映射；截获 `queryChatLog` 后，用该内存映射补充 `cid_hash`/`conversation_key`。URL 脱敏只能发生在持久化和日志输出前，不能先脱敏再丢失关联身份。

响应顶层结构：

```json
{
  "code": "string",
  "chatLogList": [
    {
      "chatLogMessageList": []
    }
  ]
}
```

`chatLogMessageList[]` 主要字段：

```text
closeSessionTime
content
created
customer
height
imgUrl
lang
mallId
mid
popRemoveMarker
sid
type
uuid
waiter
waiterSend
width
```

其中：

```text
waiterSend=true   => 客服消息
waiterSend=false  => 顾客消息
created           => 消息时间
mid               => 消息 ID，优先用于去重
uuid              => 消息 UUID，可作为第二去重身份
sid               => 会话/场次标识
imgUrl            => 图片消息地址
type              => 消息类型
content           => 文本内容或图片占位文本
```

## 5. 新链路设计

### 5.1 插件匹配范围

当前插件 `manifest.json` 只匹配旧实时工作台：

```text
https://dongdong.jd.com/*
```

新链路默认只注入京麦目标页：

```text
https://shop.jd.com/jdm/kefu/kf-manage-lite/*
```

`https://kf.jd.com/*` 可作为 host permission 用于识别页面自然 XHR URL，但不作为 content script 注入目标，也不允许 background 主动请求。

旧实时链路处理规则：

```text
本分支发布包默认不注入 dongdong.jd.com
如需兼容旧能力，必须提供 legacyRealtimeCapture 独立配置
legacyRealtimeCapture 默认 false
新“京麦聊天记录采集”启动时不得同时启动旧实时监听
```

### 5.2 来源命名

建议新增采集来源：

```text
reception_list       聊天记录列表页自然返回的会话元数据
reception_chatlog    点击“查看”后自然返回的聊天明细 JSON
reception_dom        抽屉 DOM 兜底解析
```

后端 `CaptureSource` 需要允许这些值，或把来源先统一为 `xhr` 并在 `payload.pageContext.pageType` 中标记。为了后续查询和排查，建议显式新增来源类型。

### 5.3 采集流程

推荐第一阶段实现为手动触发、受控运行：

```text
1. 客服打开京麦接待工具 -> 聊天记录
2. 客服设置时间范围和筛选项
3. 客服点击插件“采集当前查询结果”
4. 插件读取当前时间范围、当前页码、总页数
5. 插件低频点击当前页可见会话的“查看”
6. 每次抽屉打开后等待 queryChatLog 自然返回
7. 插件读取 chatLogMessageList 并上报
8. 关闭抽屉，进入下一条
9. 当前页完成后按配置决定是否进入下一页
10. 达到时间、页数、会话数、错误数任一上限后停止
```

第一阶段不自动设置筛选项，不自动扩大日期范围，由客服先在页面上确认查询条件。

### 5.4 运行限制

建议默认限制：

```text
单次最多页数：3
单次最多会话：30
单次最长运行：5 分钟
点击“查看”间隔：800-1500ms
抽屉等待超时：8s
连续失败上限：3
分页等待：1500-2500ms
同一 cid_hash 同一运行只采一次
```

可配置但不建议默认放开：

```text
更大页数
更长时间范围
按客服组批量采集
按顾客 ID 批量补采
```

## 6. 数据规范化

### 6.1 conversation 映射

建议将每条列表会话写成 conversation 元数据：

```text
platform              jd_jingmai_reception
cid_hash              sha256("cid:" + cid)，只在内存和脱敏 raw 中出现
conversation_key      sha256(platform + cid_hash)
source_conversation_hash cid_hash；不保存原始 cid
customer_pin_hash     hash(customer)
customer_name         不保存明文或仅在授权环境保存
seller_pin_hash       hash(service)
seller_app            jingmai.waiter
customer_app          jingmai.customer
session_type          sessionType/sessionTypeDesc
vender_name           mallName
raw_customer          脱敏后的列表项 JSON，只允许 cid_hash，不允许原始 cid/customer/service
last_message_at       max(chatLogMessageList.created)
```

当前数据库没有 `source_conversation_id` 字段，第一阶段不要新增原始 `cid` 字段。可以在 `raw_customer` 中保存 `cid_hash` 和脱敏后的列表字段；后续若要可读排查，也只新增 `source_conversation_hash`，不新增原始 `cid`。

### 6.2 message 映射

`chatLogMessageList[]` 到 `messages`：

```text
platform          jd_jingmai_reception
conversation_key  sha256(platform + cid_hash)
msg_id            mid 存在时用 jm:{cid_hash}:{mid}，否则用 jm:{cid_hash}:{uuid}
mid               mid 可转整数时写入
local_id          sid
direction         waiterSend ? seller_or_waiter : customer_or_external
top_type          chat_log_message
body_type         imgUrl ? image : text
content           content
media_url         imgUrl
media_width       width
media_height      height
message_at        created 按 Asia/Shanghai 解析后转 ISO
lang              lang
from_pin_hash     waiterSend ? hash(waiter) : hash(customer)
to_pin_hash       waiterSend ? hash(customer) : hash(waiter)
source            reception_chatlog
raw_json          脱敏后的原始消息 JSON，只允许 cid_hash，不允许原始 cid/customer/waiter
captured_at       插件采集时间
```

图片消息：

```text
imgUrl 非空 => body_type=image
content 可保留平台显示文本，例如“预览”
media_url=imgUrl
width/height 写入 media_width/media_height
```

## 7. 去重策略

优先级：

```text
1. platform + cid_hash + mid
2. platform + cid_hash + uuid
3. platform + cid_hash + sid + created_iso + waiterSend + type + content_hash + imgUrl
```

原因：

```text
cid_hash 标识一次咨询会话，原始 cid 不持久化
mid 是消息级身份，优先级最高
uuid 也是消息身份，但需观察是否跨会话唯一
fallback 兜底处理缺 mid/uuid 的图片、系统消息或异常消息
```

建议 `eventId`：

```text
reception-chatlog:{cid_hash}:{mid}
reception-chatlog:{cid_hash}:{uuid}
reception-chatlog:{cid_hash}:{fallback_hash}
```

数据库层仍以 `messages.dedupe_key UNIQUE` 保底。重复采同一时间范围时，应返回 duplicate 或 update，不新增重复消息。

## 8. 后端改造点

### 8.1 models

`CaptureSource` 增加：

```text
reception_list
reception_chatlog
reception_dom
```

### 8.2 normalize

新增京麦聊天记录格式识别：

```text
如果 event.source == reception_chatlog
读取 event.conversation.cid_hash 或 event.payload.session.cid_hash
读取 message.mid/uuid/sid/created/waiterSend/imgUrl/type/content
按第 6 节映射为标准 conversation/message
```

平台分流要求：

```text
reception_chatlog/reception_dom 使用 platform=jd_jingmai_reception
旧 dongdong source 继续使用 platform=jd_dongdong
normalize 不能继续依赖单一全局 PLATFORM 常量
dedupe_key 计算必须使用动态 platform
```

时间解析要求：

```text
created 形如 2026-08-19 21:12:33
按 Asia/Shanghai 本地时间解析
落库前转换为 ISO 字符串
解析失败时保留 raw_json，但 message_at 置空并记录 rejection/metadata
```

必须继续脱敏：

```text
customer
waiter
service
cid
sid
uuid
toCid
appId
mallId
pin
cookie
token
sign
authorization
```

### 8.3 repositories

现有 `upsert_message` 可继续复用。需要确认：

```text
mid 可能超过 SQLite INTEGER 安全范围时不能强转失败
同一消息先以 fallback 入库、后以 mid 入库时能复用身份
source 合并时保留 reception_chatlog/reception_dom
```

### 8.4 viewer

可选增强：

```text
来源过滤支持 reception_chatlog
列表展示 platform 或来源标签
最近事件元数据展示 pageType=ReceptionTools
```

## 10. 状态机

```text
idle
  -> ready             当前页面是聊天记录查询页
  -> collecting_list   等待/读取当前列表
  -> opening_detail    点击查看
  -> collecting_detail 等待 queryChatLog 或解析 DOM
  -> closing_detail    关闭抽屉
  -> next_row          下一条
  -> next_page         下一页
  -> finished          达到上限或完成
  -> stopped           用户停止
  -> failed            连续失败超限
```

任何状态都必须响应停止。

## 12. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 批量点击过快 | 触发风控或页面异常 | 低频、上限、人工启动、可停止 |
| 页面 DOM class 变化 | DOM 兜底失效 | 优先解析 queryChatLog JSON，DOM 仅校验 |
| queryChatLog 字段变化 | 消息解析失败 | 保留 raw_json 脱敏样本，测试覆盖字段缺失 |
| mid/uuid 缺失 | 重复入库 | fallback 去重包含 cid_hash/created_iso/direction/type/content/imgUrl |
| 图片很大 | 本地缓存压力 | 第一阶段只保存 media_url，图片缓存沿用现有可配置逻辑 |
| 客户/客服明文泄露 | 合规风险 | hash 标识符，控制台和文档不输出明文 |
| 误点发起新会话 | 业务扰动 | 选择器白名单只允许当前行 text=查看 |
| 用户设置超大时间范围 | 页面压力大 | 单次页数/会话数/时长上限 |

## 14. 最终建议

第一版只做“人工确认筛选条件后，采集当前查询结果的前 N 页”。这样可以满足“抓取一定时间内客服客户聊天记录并去重入库”，同时避免从后端模拟接口、避免无限批量拉取、避免误触发业务动作。

实现优先级：

```text
1. 后端支持 reception_chatlog 规范化和去重
2. 插件支持 shop.jd.com 页面识别
3. 被动截获 queryChatLog 并上报
4. 手动按钮触发当前页逐条查看
5. 受控分页
```

不建议第一版做：

```text
自动跨 13 个月全量抓取
自动按所有客服组循环
服务端直接请求 kf.jd.com
自动点击“切换为该用户全部聊天信息”
自动发起新会话
```
