# 京麦接待工具聊天记录采集方案

文档日期：2026-08-19
当前分支：`feature/reception-chatlog-capture`
目标页面：`https://shop.jd.com/jdm/kefu/kf-manage-lite/#/UtilsSetting/ReceptionTools`
业务入口：接待工具 -> 聊天记录
当前结论：新需求应从原“咚咚实时工作台采集”拆出独立链路，围绕京麦“聊天记录”查询页做受控时间范围采集、去重和入库。
隔离补充：京麦接待记录和旧咚咚实时采集是两套不同业务逻辑，代码入口、上报 API、队列、数据库表必须隔离；新链路不得写入旧 `conversations/messages/capture_events` 表，也不得依赖旧 `normalize_capture_event`。

## 1. 需求变化

原方案围绕 `https://dongdong.jd.com/` 工作台：

```text
实时监听当前工作台收到的聊天记录
读取 window.session
解析 #t-chat-scroll 当前会话 DOM
可选被动监听 fetch/XHR/WebSocket
```

新需求变为：

```text
不再抓取网页实时聊天记录
从京麦“接待工具 / 聊天记录”页面采集一定时间范围内的客服客户聊天记录
点击列表行“查看”后，右侧抽屉中展示该会话最新聊天记录
采集后去重入库
```

因此需要新分支开发，不应继续把逻辑塞进现有咚咚工作台 DOM/session 采集路径。本分支默认只启用京麦聊天记录链路；旧 `dongdong.jd.com` 实时链路如需保留，必须拆成独立 legacy 开关并默认关闭。

## 2. 采集边界

### 2.1 允许

```text
在客服本人已登录京麦后台的浏览器页面内采集
读取聊天记录列表页自然返回的查询结果
点击“查看”打开当前页右侧聊天明细抽屉
读取右侧抽屉 DOM 中已经渲染的消息
被动截获页面自然触发的 queryList/queryChatLog XHR 响应
按用户指定时间范围、页数上限、会话上限低频采集
将规范化消息上报本机采集网关
幂等入库
```

### 2.2 禁止

```text
点击“发起新会话”
点击“举报”
导出平台数据
绕过京麦登录
复用 cookie、token、sign、aid 等鉴权参数到独立后端批量调用
从服务端直接模拟京麦接口批量拉取
高频翻页、并发打开、无限制遍历全部历史
自动发送、标记、转接、改客服状态
把客户 pin、订单、正文等敏感信息写入日志、文档或普通控制台输出
```

## 4. 网络接口观察

### 4.2 聊天明细

点击列表行 `查看` 后自然触发：

```text

```

注意：`queryChatLog` 响应体本身不包含 `cid`。插件必须在点击 `查看` 前，从当前列表行或最近一次 `queryList.waiterSessionList[]` 建立 `row -> cid` 的内存映射；截获 `queryChatLog` 后，用该内存映射补充 `cid_hash`/`conversation_key`。URL 脱敏只能发生在持久化和日志输出前，不能先脱敏再丢失关联身份。

## 5. 新链路设计

### 5.1 插件匹配范围

当前插件 `manifest.json` 只匹配旧实时工作台：

```text
https://dongdong.jd.com/*
```

新链路默认只注入京麦目标页：

```text
https://shop.jd.com/jdm/kefu/kf-manage-lite/*
```

`https://kf.jd.com/*` 可作为 host permission 用于识别页面自然 XHR URL，但不作为 content script 注入目标，也不允许 background 主动请求。

旧实时链路处理规则：

```text
本分支发布包默认不注入 dongdong.jd.com
如需兼容旧能力，必须提供 legacyRealtimeCapture 独立配置
legacyRealtimeCapture 默认 false
新“京麦聊天记录采集”启动时不得同时启动旧实时监听
```

### 5.2 来源命名

京麦接待记录使用独立模型 `ReceptionSource`，不加入旧实时链路的 `CaptureSource`。

建议独立来源：

```text
reception_chatlog    点击“查看”后自然返回的聊天明细 JSON
reception_dom        抽屉 DOM 兜底解析
```

`reception_list` 只作为插件内存态列表缓存，不作为入库事件。后端独立接收：

```text
POST /reception/chatlog/events
```

旧实时接口继续只处理：

```text
POST /capture/events
```

### 5.3 采集流程

推荐第一阶段实现为手动触发、受控运行：

```text
1. 客服打开京麦接待工具 -> 聊天记录
2. 页面默认展示当天数据，插件不主动改日期筛选
3. 插件点击当前条件下的“查询”，读取当天总条数和总页数
4. 当天尚未完成全量时，插件从第 1 页开始按页面总页数全量翻页
5. 插件低频点击每条可见会话的“查看”
6. 每次抽屉打开后等待 queryChatLog 自然返回
7. 插件读取 chatLogMessageList 并上报
8. 关闭抽屉，进入下一条
9. 当前页完成后进入下一页，直到当天页面总页数完成或达到安全上限
10. 全量完成后进入周期增量巡检
```

第一阶段不自动扩大日期范围，不切客服组，不改客户筛选；它只使用页面默认当天条件和当前页面已有筛选项。

同一天日期范围内如果弹窗明细持续新增消息，采用“重复当前查询 + 幂等入库”的增量策略：

```text
1. 自动增量巡检默认开启
2. content-isolated 在当前京麦聊天记录页面按间隔启动独立 refresh run
3. 每个 refresh run 先点击页面现有筛选条件下的“查询”，尽量回到第 1 页
4. 当天全量未完成时运行 backfill_today，按页面总页数全量翻页
5. 当天全量已完成时运行 incremental，只巡检前 N 页最新会话
6. queryChatLog 返回的历史消息和新增消息一起上报
7. 后端以 conversation_key 合并会话，以 dedupe_key 跳过重复消息
8. 新增消息插入 reception_chatlog_messages，并把会话 last_message_at 保持为最大消息时间
9. 如果增量巡检发现新增总量超过本轮覆盖行数，标记当天需要重新全量补抓
```

自动增量巡检不自动修改页面日期、客服组、客户等筛选条件。

### 5.4 运行限制

建议默认限制：

```text
单次最多页数：500
单次最多会话：10000
单次最长运行：120 分钟
点击“查看”间隔：800-1500ms
抽屉等待超时：8s
连续失败上限：20
分页等待：1500-2500ms
每日全量补抓：默认开启
自动增量巡检：默认开启
增量巡检页数：默认 5 页
自动刷新间隔：默认 3 分钟
追平确认轮数：默认 2
```

可配置但不建议默认放开：

```text
更大页数
更长时间范围
按客服组批量采集
按顾客 ID 批量补采
```

## 6. 数据规范化

京麦接待记录不写旧实时表：

```text
conversations
messages
capture_events
```

独立写入：

```text
reception_chatlog_sessions
reception_chatlog_messages
reception_chatlog_events
```

### 6.1 conversation 映射

建议将每条列表会话写成 `reception_chatlog_sessions` 元数据：

```text
platform              jd_jingmai_reception
cid_hash              sha256("cid:" + cid)，只在内存和脱敏 raw 中出现
conversation_key      sha256(platform + cid_hash)
customer_hash         hash(customer)
waiter_hash           hash(service)
session_type          sessionType/sessionTypeDesc
mall_name             mallName
raw_session           脱敏后的列表项 JSON，只允许 cid_hash，不允许原始 cid/customer/service
last_message_at       max(chatLogMessageList.created)
```

第一阶段不要新增原始 `cid` 字段。可以在 `raw_session` 中保存 `cid_hash` 和脱敏后的列表字段；后续若要可读排查，也只新增 hash 字段，不新增原始 `cid`。

### 6.2 message 映射

`chatLogMessageList[]` 到 `reception_chatlog_messages`：

```text
conversation_key  sha256(platform + cid_hash)
msg_id            mid 存在时用 jm:{cid_hash}:{mid}，否则用 jm:{cid_hash}:{uuid}
mid               以文本写入，避免和旧 SQLite INTEGER 约束耦合
local_id          hash(sid) 或 sidHash，不保存原始 sid
direction         waiterSend ? seller_or_waiter : customer_or_external
body_type         imgUrl ? image : text
content           content
media_url         imgUrl
media_width       width
media_height      height
message_at        created 按 Asia/Shanghai 解析后转 ISO
lang              lang
from_hash         waiterSend ? hash(waiter) : hash(customer)
to_hash           waiterSend ? hash(customer) : hash(waiter)
source            reception_chatlog
raw_json          脱敏后的原始消息 JSON，只允许 cid_hash，不允许原始 cid/customer/waiter
captured_at       插件采集时间
```

图片消息：

```text
imgUrl 非空 => body_type=image
content 可保留平台显示文本，例如“预览”
media_url=imgUrl
width/height 写入 media_width/media_height
```

## 7. 去重策略

优先级：

```text
1. platform + cid_hash + mid
2. platform + cid_hash + uuid
3. platform + cid_hash + sid + created_iso + waiterSend + type + content_hash + imgUrl
```

原因：

```text
cid_hash 标识一次咨询会话，原始 cid 不持久化
mid 是消息级身份，优先级最高
uuid 也是消息身份，但需观察是否跨会话唯一
fallback 兜底处理缺 mid/uuid 的图片、系统消息或异常消息
```

建议 `eventId`：

```text
reception-chatlog:{cid_hash}:{mid}
reception-chatlog:{cid_hash}:{uuid}
reception-chatlog:{cid_hash}:{fallback_hash}
```

数据库层仍以 `reception_chatlog_messages.dedupe_key UNIQUE` 保底。重复采同一时间范围时，应返回 duplicate 或 update，不新增重复消息。

## 8. 后端改造点

### 8.1 独立模型

不要修改旧实时链路 `CaptureSource`。京麦接待记录新增独立模型：

```text
reception_chatlog
reception_dom
```

对应独立上报入口：

```text
ReceptionChatLogBatchIn
ReceptionChatLogEventIn
POST /reception/chatlog/events
```

### 8.2 独立 normalize

新增京麦聊天记录格式识别到独立模块，例如 `jdchat_gateway/reception.py`：

```text
读取 event.conversation.cid_hash 或 event.payload.session.cid_hash
读取 message.mid/uuid/sid/created/waiterSend/imgUrl/type/content
按第 6 节映射为 reception session/message
```

隔离要求：

```text
旧 normalize_capture_event 只处理 dongdong 实时事件
京麦接待记录不得调用旧 upsert_conversation/upsert_message
京麦接待记录不得写旧 conversations/messages/capture_events
```

时间解析要求：

```text
created 形如 2026-08-19 21:12:33
按 Asia/Shanghai 本地时间解析
落库前转换为 ISO 字符串
解析失败时保留 raw_json，但 message_at 置空并记录 rejection/metadata
```

必须继续脱敏：

```text
customer
waiter
service
cid
sid
uuid
toCid
appId
mallId
pin
cookie
token
sign
authorization
```

### 8.3 独立 repositories

新增独立 repository 方法：

```text
upsert_reception_chatlog_session
upsert_reception_chatlog_message
record_reception_chatlog_event
```

独立表：

```text
reception_chatlog_sessions
reception_chatlog_messages
reception_chatlog_events
```

### 8.4 viewer / 查询 API

可选增强：

```text
GET /reception/chatlog/sessions
GET /reception/chatlog/sessions/{conversation_key}/messages
GET /reception/chatlog/stats
```

### 9.2 页面识别

新增页面类型判断：

```js
function isReceptionToolsPage() {
  return location.hostname === "shop.jd.com"
    && location.pathname.includes("/jdm/kefu/kf-manage-lite/")
    && location.hash.includes("/UtilsSetting/ReceptionTools");

```

### 9.3 XHR 被动截获

对 `queryList` 和 `queryChatLog` 做专门解析：

```text
waiterSession/jingmai/queryList    => 提取 waiterSessionList
waiterSession/queryChatLog         => 提取 chatLogMessageList
```

注意：

```text
只观察页面自然触发的 XHR
不从插件后台主动调用 kf.jd.com
内部可在内存中读取 cid；URL 日志、eventId、raw_json、payload 持久化前必须替换为 cid_hash
响应体不要完整写控制台
safeClone/isSensitiveKey 需要扩展 customer、waiter、service、cid、sid、uuid、appId、mallId、toCid
```

### 9.4 DOM 兜底

如果未截获到 `queryChatLog`，可在抽屉打开后解析 DOM：

```text
.chat-log-info-title .name       => waiter/customer
.msg-block                       => message
.msg-info .name                  => sender
.msg-time                        => created
.msg-content                     => content
.msg-content img                 => image
```

DOM 兜底缺少 `mid/uuid`，去重只能使用 fallback，因此优先级低于 XHR。

### 9.5 控制 UI

插件弹窗建议新增“京麦聊天记录采集”区：

```text
当前页面状态
当前筛选时间
当前页 / 总页
单次最大页数
单次最大会话数
开始采集当前查询结果
停止
最近采集状态
队列长度
```

默认不自动运行，必须人工点击开始。

### 9.6 上报隔离

插件后台使用独立队列和独立端点：

```text
receptionQueue  -> POST /reception/chatlog/events
queue           -> POST /capture/events
```

路由规则：

```text
event.source startsWith("reception_") => receptionQueue
其它旧实时事件                         => queue
```

`captureReceptionChatLog` 默认 true，`captureLegacyRealtime` 默认 false。两条队列可以共享本机网关地址和 token，但不能共享 endpoint 或数据库表。

```text
  -> collecting_list   等待/读取当前列表
  -> opening_detail    点击查看
  -> collecting_detail 等待 queryChatLog 或解析 DOM
  -> closing_detail    关闭抽屉
  -> next_row          下一条
  -> next_page         下一页
  -> finished          达到上限或完成
  -> stopped           用户停止
  -> failed            连续失败超限
```

任何状态都必须响应停止。

## 12. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 批量点击过快 | 触发风控或页面异常 | 低频、上限、人工启动、可停止 |
| 页面 DOM class 变化 | DOM 兜底失效 | 优先解析 queryChatLog JSON，DOM 仅校验 |
| queryChatLog 字段变化 | 消息解析失败 | 保留 raw_json 脱敏样本，测试覆盖字段缺失 |
| mid/uuid 缺失 | 重复入库 | fallback 去重包含 cid_hash/created_iso/direction/type/content/imgUrl |
| 图片很大 | 本地缓存压力 | 第一阶段只保存 media_url，图片缓存沿用现有可配置逻辑 |
| 客户/客服明文泄露 | 合规风险 | hash 标识符，控制台和文档不输出明文 |
| 误点发起新会话 | 业务扰动 | 选择器白名单只允许当前行 text=查看 |
| 用户设置超大时间范围 | 页面压力大 | 单次页数/会话数/时长上限 |

## 14. 最终建议

第一版只做“人工确认筛选条件后，采集当前查询结果的前 N 页”。这样可以满足“抓取一定时间内客服客户聊天记录并去重入库”，同时避免从后端模拟接口、避免无限批量拉取、避免误触发业务动作。

实现优先级：

```text
1. 后端支持 reception_chatlog 规范化和去重
2. 插件支持 shop.jd.com 页面识别
3. 被动截获 queryChatLog 并上报
4. 手动按钮触发当前页逐条查看
5. 受控分页
```

不建议第一版做：

```text
自动跨 13 个月全量抓取
自动按所有客服组循环
服务端直接请求 kf.jd.com
自动点击“切换为该用户全部聊天信息”
自动发起新会话
```
