# 京东咚咚聊天记录被动采集方案

文档日期：2026-09-09  
适用对象：京东咚咚工作站中，客服本人已登录、已授权使用的客服辅助记录与后续客服 Agent 自动回复研发  
当前结论：建议采用“被动读取 + 本地队列 + 幂等落库 + 合规控制”的浏览器插件 MVP，不建议做接口级批量同步器。

实测调整：MVP 默认只读取页面前端状态 `window.session` 和当前会话 DOM 渲染消息，不默认包装 WebSocket / fetch / XHR。网络 hook 会提高页面兼容性和平台风控风险，只保留为显式实验开关，必须单独评估后启用。

## 1. 背景和目标

目标是在京东咚咚工作站中采集客服与客户的聊天记录，保存到自有数据库，供后续开发客服 Agent 自动回复、质检、知识沉淀、售后问题归因使用。

实际业务场景是一个客服会同时对接多个客户，每个客户对话不定时出现新消息。插件不能只围绕当前打开的聊天窗口做抓取，否则会漏掉未打开会话的新消息。

因此方案目标分为三层：

1. 实时记录工作台收到的新消息。
2. 记录当前打开会话中已渲染的历史和上下文消息。
3. 通过幂等落库把网络事件、前端状态、DOM 渲染三类来源合并为一条可信消息流。

## 3. 风险判断

### 3.1 低到中风险

这些动作只读取客服本人已登录页面中已经可见或前端已持有的数据，反爬和账号风险相对较低：

```text
读取当前会话 DOM
读取 window.session.customer
读取 window.session.messages()
监听 #t-chat-scroll 的 DOM 增量变化
被动观察页面已经收到的 WebSocket / XHR / fetch 消息
本地队列缓存后批量上传自有后端
```

### 3.2 中风险

这些动作需要受控开关、频率限制和日志审计：

```text
自动向上滚动当前已打开会话，加载更早历史
自动扫描左侧会话列表摘要
把完整聊天内容上传到后端
在多个客服账号上部署插件
```

### 3.3 高风险，不建议实施

以下动作容易触发风控、限流、账号异常，也可能违反平台规则：

```text
复用咚咚 token、aid、sign、access_token 等参数
模拟 WebSocket 协议
主动请求历史消息接口
批量拉取多个客户历史记录
跨店铺、跨账号集中抓取
非人工在线状态下后台抓取
规避指纹、自动化检测、白名单或埋点
自动发送、自动标记已读、自动转接、自动改客服状态
```

技术边界应写入代码：插件默认禁止调用任何会改变会话状态的方法。

禁用方法关键字：

```text
send
sendPipe
createMessage
read
readAck
sendAck
receipt
setStatus
delSession
transferToGroup
transferToClass
rovekeMessage
logout
```

## 4. 推荐总体架构

```text
Chrome Extension
  ├─ content-isolated.js
  │   ├─ 接收页面 MAIN world 的 postMessage
  │   ├─ DOM 兜底解析
  │   ├─ 数据脱敏/规范化
  │   └─ 发送到 background 队列
  │
  ├─ injected-main.js
  │   ├─ 读取 window.session.customer
  │   ├─ 读取 window.session.messages()
  │   ├─ 被动 hook WebSocket / fetch / XHR
  │   ├─ 不主动请求京东接口
  │   └─ 不读取或上报 token/cookie
  │
  ├─ background.js
  │   ├─ IndexedDB 本地队列
  │   ├─ 幂等去重
  │   ├─ 批量上传后端
  │   ├─ 失败重试
  │   └─ 插件开关/状态上报
  │
  └─ options.html
      ├─ 后端地址
      ├─ 商家内部授权标识
      ├─ 采集开关
      ├─ 脱敏策略
      └─ 保留周期配置

Backend
  ├─ POST /api/capture/events
  ├─ POST /api/capture/heartbeat
  ├─ conversations
  ├─ messages
  ├─ capture_events
  └─ audit_logs
```

核心原则：

```text
页面收到什么，插件记录什么。
页面渲染什么，插件补齐什么。
插件不主动向京东要更多。
插件不改变客服工作台状态。
```

## 5. 采集策略

### 5.1 工作台级实时监听

多客户并发场景下，当前 DOM 只代表当前打开的会话。实时消息应优先来自工作台级事件。

插件应在页面 `MAIN world` 注入被动监听：

```js
const NativeWebSocket = window.WebSocket

window.WebSocket = function (...args) {
  const ws = new NativeWebSocket(...args)

  ws.addEventListener('message', (event) => {
    // 只观察页面已经收到的数据
    // 不修改 event.data，不阻断页面逻辑
    window.postMessage({
      source: 'jdchat-capture',
      kind: 'ws-message',
      payload: safeSummarize(event.data),
      capturedAt: Date.now()
    }, '*')
  })

  return ws
}

window.WebSocket.prototype = NativeWebSocket.prototype
```

注意事项：

```text
不记录 WebSocket URL 中的 token、aid、sign、pin 等敏感参数
不主动创建新 WebSocket
不发送 WebSocket 消息
不修改页面接收的消息
```

### 5.2 XHR / fetch 被动观察

只监听页面自身发出的请求响应，用于捕获页面加载会话、历史、客户列表时已经返回的数据。

限制：

```text
不主动调用 api-dd.jd.com
不主动调用 vp.jd.com
不复用 request body
不复用鉴权参数
不突破页面当前权限
```

### 5.3 前端状态对账

每 2-5 秒读取一次页面内存状态，仅做本地对账：

```js
const customer = window.session?.customer
const messages = window.session?.messages?.()
```

对账用途：

```text
补偿插件注入晚导致的漏采
补偿 WebSocket hook 解析失败
补偿页面重连或刷新后的状态恢复
获取当前会话 customer 元数据
```

频率建议：

```text
默认 5 秒
窗口不可见时降到 15-30 秒
页面空闲或无 active customer 时暂停 DOM 扫描
```

### 5.4 DOM 兜底监听

监听当前打开会话消息区域：

```js
const root = document.querySelector('#t-chat-scroll')

const observer = new MutationObserver((mutations) => {
  for (const mutation of mutations) {
    for (const node of mutation.addedNodes) {
      if (node.nodeType !== Node.ELEMENT_NODE) continue
      parseMessageDom(node)
    }
  }
})

observer.observe(root, {
  childList: true,
  subtree: true
})
```

DOM 解析规则：

```text
.message                         => 顶层消息块
.message_right                   => 客服/商家侧
.message_left                    => 客户侧
.message_center                  => 系统/分隔
.message__nickname               => 昵称和展示时间容器
.message__time_str               => 展示时间
.message__content                => 文本内容
.message__image-wrap img         => 图片内容
.CardWrapper.ProductCard         => 商品/卡片消息
.message__read_status.read       => 已读状态，仅记录展示状态，不触发 read/readAck
```

DOM 采集是兜底，不是主数据源。原因：

```text
只覆盖当前打开会话
可能因虚拟滚动只保留部分历史
结构和 CSS class 可能随前端版本变化
文本内容可能混入昵称、时间、已读状态
```

## 6. 多客户会话处理

### 6.1 conversation_key

每条消息都要归属到一个会话。推荐 key：

```text
platform = jd_dongdong
vender_id = customer.venderId 或 body.chatinfo.venderId
customer_app = 客户侧 app
customer_pin = 客户侧 pin
session_type = customer.sessionType 或消息推断
```

组合：

```text
conversation_key =
  sha256(platform + ':' + vender_id + ':' + customer_app + ':' + customer_pin + ':' + session_type)
```

### 6.2 客户侧识别

结构化消息中：

```js
const ownApp = window.session.app
const ownPin = window.session.pin

function inferParties(msg) {
  const fromIsSelf =
    msg.from?.app === ownApp ||
    msg.from?.pin === ownPin

  if (fromIsSelf) {
    return {
      direction: 'seller_or_waiter',
      seller: msg.from,
      customer: msg.to
    }
  }

  return {
    direction: 'customer_or_external',
    seller: msg.to,
    customer: msg.from
  }
}
```

### 6.3 未打开客户的新消息

未打开客户的消息应通过工作台级事件捕获：

```text
WebSocket message
XHR/fetch response
左侧会话列表新增/摘要变化
```

如果只依赖 `#t-chat-scroll`，未打开客户的新消息一定会漏。

### 6.4 会话列表索引

左侧列表可作为索引，不作为完整消息源：

```text
#t-alluser-wrap
.alluser-item
.alluser-item-name
.alluser-item-date-w
.alluser-item-breifmsg
.c_stream-item-w
```

用途：

```text
发现新会话
记录未读数变化
记录最后一条摘要
补充 customer name / pin / app
```

禁止：

```text
不要自动点击客户列表逐个打开
不要自动切换会话以批量抓历史
```

以下以 PostgreSQL 为例。

```sql

CREATE INDEX idx_jd_conversations_vender
  ON jd_conversations (vender_id);
```


### 7.2 messages

```sql
CREATE TABLE jd_messages (

  from_pin_hash TEXT,
  from_client_type TEXT,
  from_art TEXT,
  to_app TEXT,

  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),

CREATE UNIQUE INDEX uq_jd_messages_msg_id
  ON jd_messages (platform, msg_id)
```

## 8. 消息规范化

### 8.1 统一消息模型

```ts
type NormalizedJdMessage = {
  platform: 'jd_dongdong'
  conversationKey: string
  msgId?: string
  mid?: number
  direction: 'customer_or_external' | 'seller_or_waiter' | 'system' | 'unknown'
  topType?: string
  bodyType?: 'text' | 'image' | 'template2' | string
  content?: string
  contentHash?: string
  media?: {
    url?: string
    width?: number
    height?: number
    size?: number
  }
  templatePayload?: unknown
  messageAt?: string
  from: {
    app?: string
    pinHash?: string
    clientType?: string
    art?: string
  }
  to: {
    app?: string
    pinHash?: string
  }
  source: 'websocket' | 'xhr' | 'fetch' | 'session' | 'dom' | 'manual_scroll'
  rawJson?: unknown
  capturedAt: string
}
```

### 8.2 去重优先级

```text
1. msg.id
2. conversation_key + mid
3. conversation_key + timestamp + direction + body_type + content_hash
```

### 8.3 时间字段

优先级：

```text
timestamp
datetime
clientTime
DOM message__time_str + 当前日期上下文
captured_at
```

保留原始毫秒字段：

```text
client_time
datetime
timestamp
```

统一查询字段：

```text
message_at TIMESTAMPTZ
```

## 11. 历史消息补全策略

### 11.1 默认不批量补历史

生产默认只采集：

```text
当前页面已有消息
工作台运行期间新增消息
客服手动打开会话后自然加载的消息
```

### 11.2 受控历史补全

如果业务确实需要补当前会话历史，可做成手动模式：

```text
客服打开某个会话
点击插件按钮“补当前会话历史”
插件只滚动 #t-chat-scroll
每次滚动后解析 DOM 和 session.messages()
达到上限后停止
```

建议限制：

```text
单次最多 3-5 屏
单会话每天最多 1 次
每次滚动间隔 800-1500ms
遇到加载失败立即停止
不自动切换客户
不主动请求历史接口
```

### 11.3 不建议的历史补全方式

```text
批量打开左侧所有客户
按客户列表自动逐个切换
调用历史接口
复用 IM 鉴权参数拉取历史
离线状态后台补全
```

## 12. 合规和数据安全控制

聊天内容可能包含姓名、手机号、地址、订单号、售后信息、图片、发票信息、金融账户等个人信息或敏感个人信息。该系统不能按普通页面采集处理。

### 12.1 处理原则

必须满足：

```text
合法、正当、必要
目的明确
最小必要采集
公开透明
安全保护
可审计
可删除
```

### 12.2 内部授权

上线前需要明确：

```text
商家主体是谁
谁是个人信息处理者
插件由谁安装
客服是否已被告知和授权
数据用于哪些具体目的
是否委托第三方处理
是否存在跨境传输
保存多久
谁能查看明文
客户如何行使删除/查询权利
```

### 12.3 数据最小化

默认采集：

```text
消息文本
消息类型
消息时间
方向
客户和商家标识的 hash
图片 URL 或附件 URL
必要的原始字段
```

默认不采集：

```text
cookie
token
aid
sign
access_token
浏览器指纹
客服密码
非咚咚页面内容
```

建议可配置脱敏：

```text
手机号脱敏
身份证号脱敏
银行卡号脱敏
地址关键词脱敏
邮箱脱敏
订单号可选脱敏
```

### 12.4 加密和权限

```text
传输必须 HTTPS
后端数据库磁盘加密
敏感列应用层加密
客户 pin 默认 hash
客服账号默认 hash
明文查看走 RBAC
所有查询和导出写审计日志
数据导出默认脱敏
```

### 12.5 保留周期

建议默认：

```text
原始 raw_json: 7-30 天
规范化消息: 180-365 天
质检/训练样本: 脱敏后长期保存
失败队列: 7 天
审计日志: 3 年
```

超过周期自动删除或匿名化。

## 13. 与客服 Agent 的衔接

### 13.1 初期只做建议，不自动回复

客服 Agent 第一阶段只生成建议回复：

```text

售后规则
店铺知识库
```

```text
生成时间

客服是否采用
```

## 16. 主要风险和应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| DOM 结构变化 | DOM 兜底解析失效 | 主数据源依赖结构化事件，DOM 解析加版本监控 |
| session.messages 只保留部分消息 | 漏历史 | 结合网络事件和 DOM，历史只做受控补全 |
| 多客户未打开消息漏采 | 实时性不足 | 工作台级 WebSocket/XHR 被动监听 |
| 重复来源导致重复入库 | 数据污染 | msg.id/mid/content_hash 幂等 upsert |
| 客服误触自动发送 | 客诉和平台风险 | 代码禁止写入型方法和发送按钮操作 |
| 平台风控 | 账号异常 | 不主动请求接口，不复用 token，不批量拉历史 |
| 个人信息泄露 | 法律和商业风险 | 最小化、脱敏、加密、RBAC、审计、删除 |
| 第三方服务器合规 | 平台规则和委托处理风险 | 优先自有服务器，签署委托处理和安全协议 |

## 19. 结论

可行方案不是“抓京东接口”，而是“在客服本人已登录、已授权、工作台自然运行期间，被动记录页面已经收到或已经渲染的数据”。

推荐实施路线：

```text
先做当前会话只读 PoC
再做本地队列和幂等落库
再做工作台级被动实时监听
最后接入客服 Agent 建议回复
```

上线红线：

```text
不主动请求京东接口
不复用鉴权
不批量拉历史
不自动发送
不保存 token/cookie
不超出授权目的使用聊天数据
```
