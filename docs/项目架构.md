# jdchat 项目架构

## 1. 项目定位

`jdchat` 是一个面向京东咚咚工作站的被动式聊天记录采集与本地采集网关项目。

项目目标不是模拟京东 IM 协议，也不是主动批量拉取历史消息，而是在客服本人已登录、已授权、页面自然运行的前提下，被动记录工作台已经收到或已经渲染的聊天数据，保存到本地或后端数据库，为后续客服 Agent 自动回复、质检、知识沉淀和售后分析提供数据基础。

核心原则：

```text
只读采集
被动观察
幂等落库
最小必要
可关闭
可审计
不自动回复
不主动请求京东接口
```

## 2. 系统边界

### 2.1 系统内

本项目负责：

```text
浏览器插件采集咚咚工作台已收到的数据
被动监听页面自然产生的 fetch/XHR/WebSocket 网络数据
解析当前会话 DOM 中已渲染的消息
读取页面前端状态中的当前客户和消息快照
将采集事件发送到本机 Python 服务
Python 服务做规范化、去重、SQLite 入库
为后续 Agent 提供本地消息查询基础
```

### 2.2 系统外

本项目不负责：

```text
绕过京东登录
复用 cookie、token、aid、sign、access_token
模拟 WebSocket 或 IM 协议
主动请求京东历史消息接口
自动切换客户批量抓取历史
自动回复客户
自动标记已读
自动转接或修改客服状态
```

## 3. 总体架构

```text
京东咚咚工作站页面
  │
  │  已登录客服可见页面、前端状态、已渲染消息
  ▼
浏览器插件
  ├─ injected-main.js
  │   ├─ 默认读取页面前端状态和 DOM
  │   ├─ fetch / XHR / WebSocket 作为显式 Network 开关
  │   ├─ 读取 window.session.customer
  │   └─ 读取 window.session.messages()
  │
  ├─ content-isolated.js
  │   ├─ 监听 #t-chat-scroll DOM 变化
  │   ├─ 解析 .message DOM 结构
  │   ├─ 规范化基础字段
  │   └─ 发送采集事件到 background
  │
  └─ background.js
      ├─ chrome.storage.local 本地队列
      ├─ 批量上传
      ├─ 失败重试
      └─ 插件状态管理和失败重试
  │
  │  HTTP: 127.0.0.1:8765
  ▼
本机 Python 采集网关
  ├─ FastAPI
  ├─ 请求校验
  ├─ 消息规范化
  ├─ dedupe_key 计算
  ├─ SQLite upsert
  └─ 查询/健康检查 API
  │
  ▼
SQLite 本地数据库
  ├─ conversations
  ├─ messages
  ├─ capture_events
  └─ audit_logs
```

## 4. 模块职责

### 4.1 浏览器插件

插件运行在客服浏览器内，负责轻量采集和本地排队。

主要职责：

```text
发现当前是否在 dongdong.jd.com 工作站
注入 MAIN world 脚本读取页面运行时状态
被动读取页面已经持有的消息状态
在显式开启后被动监听页面自然收到的 Network 响应/帧
监听当前打开会话的 DOM 增量渲染
在客服手动进入历史咨询并打开历史会话后读取右侧已渲染消息
生成 capture event
写入插件 chrome.storage.local 队列
低频批量上报本机采集网关
```

插件禁止：

```text
点击 .send-button
写入 .EditorContent
调用 window.session.send / read / setStatus / transfer 等写入型方法
主动调用京东接口
自动点击历史咨询 tab
自动遍历历史会话行
保存或上传 token/cookie
```

### 4.2 本机 Python 采集网关

本机服务是插件和数据库之间的可信边界。

运行约束：

```text
必须先激活 conda 环境 jdchat
仅监听 127.0.0.1
默认端口 8765
默认使用 SQLite
```

主要职责：

```text
接收插件上报事件
校验事件来源和结构
统一规范化 conversation 和 message
计算 dedupe_key
使用 SQLite 幂等 upsert
记录原始 capture_event 便于排查
提供 health 和基础查询接口
```

### 4.3 SQLite 数据库

SQLite 用于 MVP 和单机试运行。

主要表：

```text
conversations   会话索引
messages        规范化消息
capture_events  原始采集事件
audit_logs      本地操作审计
```

SQLite 适用范围：

```text
单客服测试
插件采集逻辑验证
本地 Agent 原型
断网缓存和去重验证
```

不建议 SQLite 承担：

```text
多客服集中生产库
长期明文聊天内容存储
复杂权限和审计
大规模报表分析
```

正式生产应迁移到 PostgreSQL 或 MySQL。

## 5. 数据流

### 5.1 实时消息流

```text
咚咚工作站收到新消息
  -> 页面 WebSocket / XHR / fetch 回调或响应
  -> injected-main.js 在显式开启 Network 后被动观察到消息事件
  -> window.postMessage 到 content-isolated.js
  -> background.js 入队
  -> POST /capture/events
  -> Python 服务规范化
  -> SQLite upsert
```

Network 监听边界：

```text
只监听页面自己已经发出并收到的数据
不主动发起 fetch/XHR
不新建 WebSocket
不读取或上报请求头/cookie/token
不保存完整响应体
只把解析出的疑似聊天消息上报给本机网关
```

### 5.2 当前会话 DOM 兜底流

```text
当前聊天窗口渲染 .message
  -> MutationObserver 监听 #t-chat-scroll
  -> 解析 message_left / message_right / message__content
  -> 生成 DOM 来源事件
  -> 入队上报
  -> 后端按 dedupe_key 合并
```

### 5.3 前端状态对账流

```text
定时读取 window.session.customer
定时读取 window.session.messages()
  -> 生成 session snapshot
  -> 与已采集消息按 msg.id / mid / fallback hash 合并
  -> 补齐 customer、vender、session_type、last_read_mid 等字段
```

## 6. 多客户会话模型

一个客服会同时处理多个客户，因此系统以 `conversation_key` 作为聚合维度，而不是以当前打开 DOM 为唯一来源。

推荐会话 key：

```text
platform = jd_dongdong
vender_id
customer_app
customer_pin_hash
session_type
```

组合：

```text
conversation_key = sha256(
  platform + ':' +
  vender_id + ':' +
  customer_app + ':' +
  customer_pin_hash + ':' +
  session_type
)
```

方向判断优先级：

```text
1. 结构化消息 from/to 与 window.session.app/window.session.pin 对比
2. DOM class: message_right / message_left
3. 无法判断时标记 unknown，不强行归类
```

## 7. 去重入库策略

所有来源都可能重复，包括 WebSocket、XHR、session 快照和 DOM 解析。因此入库必须幂等。

统一计算 `dedupe_key`：

```text
如果有 msg.id:
  sha256("msg_id:" + platform + ":" + msg.id)

否则如果有 mid:
  sha256("mid:" + conversation_key + ":" + mid)

否则:
  sha256(
    "fallback:" +
    conversation_key + ":" +
    timestamp + ":" +
    direction + ":" +
    body_type + ":" +
    content_hash
  )
```

SQLite 使用唯一约束：

```sql
dedupe_key TEXT NOT NULL UNIQUE
```

写入方式：

```sql
INSERT INTO messages (...)
VALUES (...)
ON CONFLICT(dedupe_key) DO UPDATE SET
  updated_at = excluded.updated_at;
```

合并原则：

```text
结构化字段优先于 DOM 字段
明文 content 不被空值覆盖
media_url 不被空值覆盖
source 记录多个来源
raw_json 可按配置保存或关闭
```

## 11. Agent 衔接架构

后续客服 Agent 不直接接触京东页面，也不直接发送消息。

推荐链路：

```text
SQLite / 后端消息库
  -> 最近会话上下文查询
  -> 商品/售后/话术知识库检索
  -> Agent 生成建议回复
  -> 客服人工确认
  -> 客服手动发送
```

Agent 第一阶段只做建议：

```text
不自动发送
不点击咚咚页面
不替客服确认承诺
不绕过人工审核
```

## 13. 关键设计取舍

| 方案 | 结论 | 原因 |
| --- | --- | --- |
| 插件直接请求京东接口 | 不采用 | 风控和合规风险高 |
| 插件直接写 SQLite | 不采用 | Chrome 插件不适合直接写本机数据库文件 |
| 插件发到 127.0.0.1 Python 服务 | 采用 | MVP 简单、可控、易调试 |
| DOM 作为唯一来源 | 不采用 | 只能覆盖当前打开会话 |
| WebSocket 被动观察作为实时来源 | 谨慎采用 | 只观察页面已收到数据，不主动发包 |
| SQLite 作为 MVP 数据库 | 采用 | 单机验证足够简单 |
| SQLite 作为生产库 | 不采用 | 权限、审计、并发和备份不足 |
| Agent 自动发送 | 不采用 | 客诉和平台风险高 |
| Agent 建议回复 + 人工确认 | 采用 | 风险可控，便于评估效果 |

## 15. 架构结论

`jdchat` 的合理架构是：

```text
浏览器插件做被动采集
本机 Python 服务做可信入库边界
SQLite 做 MVP 幂等存储
后续 Agent 只读取本地/后端消息库生成建议
所有自动写入咚咚工作站的能力都不做
```

这一架构能先验证数据链路和业务价值，同时把平台风控、账号安全和个人信息合规风险控制在较低范围。
